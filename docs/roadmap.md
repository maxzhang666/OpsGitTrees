# Roadmap

状态：后续功能的讨论清单，不是已实现能力、排期或交付承诺。

首版核心范围以 [产品需求](requirements.md) 为准；本页只维护核心范围之外的候选事项。

## 后续增强

这些功能已有明确的潜在价值，但尚未纳入首版核心；表格顺序不代表固定实现顺序。

| 候选功能 | 潜在收益 | 再次讨论的重点 |
|---|---|---|
| 侧栏内切换分支 | 直接在侧栏选择分支，减少离开文件树的操作 | 当前只展示并跟随页面分支；后续讨论分支查找／分页、切换后的目录状态与在途请求处理，不在本次实现 |
| 侧栏左／右切换 | 适应不同屏幕与阅读布局，避免固定在左侧 | 后续讨论位置记忆、页面占位、调宽方向及收起入口；当前仍固定左侧，不在本次实现 |
| 文件图标风格切换 | 准备多套文件图标风格，供用户选择和切换，满足不同的识别与展示偏好 | 图标集选择、文件类型覆盖、明暗主题适配、选择记忆及资源体积；暂不实现，后续讨论 |
| 最近访问文件 | 减少多个文件之间反复跳转的成本 | 历史范围、保留数量、清除方式与界面占用 |
| 固定文件／轻量收藏 | 快速回到常用入口 | 先评估简单固定是否足够，不直接扩展成多级收藏管理器 |
| 更完整的键盘导航 | 提高连续浏览目录的效率 | 与 GitHub、浏览器快捷键的冲突，以及可发现性 |
| PR 导航增强 | 改善代码审查中的文件定位 | 先找出 GitHub 原生 PR 文件树与过滤能力未解决的具体痛点，不重复造同一套界面 |
| GitHub 连接授权 | 减少用户手动创建和维护 PAT 的成本 | 依赖后端的方案暂不采用；Device Flow 等候选需先验证完整授权、令牌续期与油猴兼容性，不能仅凭首次获取令牌不需要 secret 就承诺无后端；见 [仓库授权](authentication.md) |

## 保留议题

此前讨论中暂不值得优先做的功能全部保留在这里，以后重新评估，不作永久排除。

| 议题 | 潜在价值 | 暂不实现的原因与重评条件 |
|---|---|---|
| 代码全文搜索／索引 | 按代码内容跨文件定位 | 数据量、更新与内存成本高；需证明现有 GitHub 能力不足，并明确成本边界 |
| 独立代码阅读器 | 在脚本内阅读文件 | 与 GitHub 内容展示重复；需先证明存在原页面无法解决的阅读问题 |
| 编辑器 | 在导航过程中直接修改代码 | 涉及编辑、保存、权限等另一组能力；需重新讨论产品边界 |
| 多标签工作区 | 并排或连续阅读多个文件 | 容易演变成在线 IDE；需评估相对浏览器标签的实际收益 |
| 提交历史与 Blame 增强 | 更快理解代码演变与来源 | 优先复用 GitHub 原生页面，只有存在明确导航痛点再增强 |
| 更多主题与动画 | 满足个性化展示偏好 | 首版只跟随明暗主题并保证可读性；需权衡资源体积与维护成本 |
| AI 代码解释与总结 | 辅助理解陌生代码 | 涉及服务、密钥、费用和隐私，偏离当前文件导航主线；需单独评估 |
| GitLab、Gitee 等其他平台 | 覆盖更多代码托管场景 | 页面、认证与数据接口各不相同；需明确需求及平台适配的长期维护能力 |

## 重评规则

每次重新讨论候选项时，至少明确：

1. 解决哪个面向大众的真实场景，而不是只根据发起者个人习惯作决定。
2. 相比 GitHub 或浏览器已有能力，新增价值是什么。
3. 带来多少请求、内存、依赖与维护负担，是否仍符合轻量目标。
4. 是否引入新的授权、隐私或外部服务成本。
5. 决定纳入后，同步更新产品需求和相关设计；未决议题不能直接当作已批准需求。

无新增共识时维持现有范围，不因进入 Roadmap 就默认实现，也不将“当前不做”解释为“永远不做”。
