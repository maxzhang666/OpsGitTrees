# 目录预加载

状态：主动预加载、截断补齐、请求合并、自动续批、限流暂停与 v2 目录块缓存恢复已实现。任务 1–4 定向测试和类型检查、当前全量测试与生产构建通过；真实 ScriptCat 0.1.2 中已验收空树分支（0 路径完整）和 main（58 路径完整）。缓存命中、管理器请求计数、GM 存储成本和私有仓库授权尚未实机验证；见[实现计划](./cache-implementation-plan.md)和[技术选型记录](./technology.md#本次实现与验证记录)。

产品范围见 [产品需求](requirements.md)。本文只记录目录数据的加载与使用规则。

## 已确认行为

- 默认主动预加载当前仓库、当前分支／版本的目录元数据，不以逐层点击加载作为主要交互。
- 目录元数据包括文件路径、类型与目录关系；不预加载文件内容。
- 目录树和全仓库文件名／路径查找使用同一份索引，避免重复获取数据。
- 索引完整后，展开目录只涉及本地展示，路径查找也不需要额外的目录请求。
- 预加载全部目录数据不等于创建全部 DOM；仅为当前展开、需要展示的节点创建界面，避免大仓库拖慢页面。
- 真实的网络、权限或 API 限制不能隐藏；不承诺首次访问时所有目录立刻可用。

## 场景处理

| 场景 | 目标行为 |
|---|---|
| 首次进入仓库 | 立即开始获取当前版本的完整目录索引，不等待用户展开目录 |
| 再次访问 | 优先复用匹配版本的缓存，减少重复下载 |
| 索引完整后展开 | 在本地展示目录，不发起目录请求 |
| 文件路径查找 | 查询同一份索引；未加载完整时说明结果可能不完整 |
| 切换分支或版本 | 使用新上下文对应的索引，不能混用旧树或让旧请求覆盖新结果 |
| 超大仓库 | 主动在后台分批补齐，优先当前文件路径和可见目录，不等点击后才开始加载 |
| 加载失败或限流 | 保留可用数据并标明未完成及原因，不能显示为完整索引或空目录 |

## 已实现的数据流程

1. 从页面确认实际 commit，在线获取仓库 Metadata 和可见性。
2. 公开仓库查找当前仓库／commit／scope 的提交映射；非公开仓库始终在线解析提交以核验 Contents 权限后才能访问任何私有缓存。
3. 按根 tree SHA 优先查完整递归响应；若缺失或存在 split 标记则使用非递归枚举；对每个子目录重复本地恢复，只有缺失块进入网络队列。
4. 响应按 SHA 与递归模式合并，但分别挂载到所有路径前缀；截断与非递归响应仍遵守统一的完整性证明。
5. 取得的路径先并入索引并显示，再由该工作槽等待对应响应的 GM 写入；最多两个槽同时包含读取／请求／发布，不建立不受限后台写队列。
6. 缓存命中不计入最多 40 个新增 Tree HTTP 请求的批次，也不被低额度或实际限流屏障阻止；缺失请求仍受 2 路并发、保留额度和 Retry-After/reset 限制。

每轮仅从匹配 commit、scope 的有效目录块重建索引与子任务；队列未持久化。路径集合与完整状态分开判定，缓存命中或队列耗尽不意味着完整。
- 根 SHA 为 Git 规范空树 SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904` 时，预加载器不发送根 Tree 请求，发布零路径完整索引；其他根 SHA 的 404 仍保持失败状态。此路径仍经过 `main` 的仓库 Metadata、提交与 Contents 授权流程。

生产构建、单键格式和回收策略见[技术设计](architecture.md)与[缓存实现计划](cache-implementation-plan.md)。当前受控检查不是真实 ScriptCat 持久化或请求计数证明。

## 缓存约束

- 缓存要区分仓库及实际版本；不能仅凭仓库名或分支名长期判定数据有效，因为分支内容会变化。
- 再访时可先使用缓存，但必须确认它是否对应当前版本；不匹配时不能标为当前完整索引。
- 同一上下文的重复请求应合并；复用数据，避免每次文件切换都重新获取整棵树。
- 切换仓库或分支后，旧请求结果不得覆盖当前视图。
- 缓存需要有容量边界与清理规则，避免长期使用时无界增长；初始额度及淘汰策略见 [技术设计](architecture.md)。
- 非公开缓存按当前授权代号隔离，并在访问／破坏性清理前复核授权；授权变化会停止旧任务。凭据边界见[仓库授权](authentication.md#授权操作设计)。

目录块持久化与刷新后恢复已实现；缓存键、升级边界和未验收场景见[目录缓存设计](./cache-design.md)及[实现计划](./cache-implementation-plan.md)。

## 平台约束

以下是 GitHub 官方接口约束，不是脚本人为设置的功能门槛；实现时仍应核对最新文档与响应。

### 递归响应截断

[Git Trees API](https://docs.github.com/en/rest/git/trees#get-a-tree) 的递归结果上限为 100,000 个条目或 7 MB，返回结果可能包含 `truncated: true`。

不能把一次递归请求等同于完整仓库索引。官方建议在结果被截断时以非递归方式获取树，再逐个获取子树；具体调度需要兼顾当前路径优先与请求成本。

### 请求限流

[REST API 限流说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api) 中，未认证公开数据请求通常按来源 IP 限制为 60 次／小时；个人认证请求的常见主限额为 5,000 次／小时，仍可能遇到次级限流。

- 不以提高并发代替请求预算控制，尤其不能无界遍历大仓库子树。
- 根据响应中的限流信息暂停后台补齐，并向用户说明原因；限流期间不持续重试。
- 公开仓库不强制认证，但不能承诺匿名额度足以覆盖任何仓库与使用频率。
- 不将私有令牌或应用密钥写入公开脚本；授权边界与凭据处理见 [仓库授权](authentication.md)。

## 方案取舍

| 方案 | 收益与代价 | 当前结论 |
|---|---|---|
| 点击目录才请求 | 初始请求少，但用户每深入一层都可能等待网络 | 不作为默认策略 |
| 无界递归拉取全部子树 | 主动加载，但可能耗尽请求额度、抢占网络与内存 | 不采用 |
| 优先完整递归索引，截断后受控后台补齐 | 常规仓库减少请求，大仓库保持主动加载；需要处理完整性和限流 | 已实现；真实超大仓库验证仍待完成 |

加载状态、请求预算、并发上限、版本检查与缓存容量的实现选择见 [技术设计](architecture.md)，验证顺序见 [开发计划](development-plan.md)。主动预加载仍是默认行为，不退回逐层点击加载。
