# 技术选型

状态：首版已有 TypeScript 实现、pnpm 锁文件及自包含生产脚本。逻辑检查、生产构建和下述浏览器表面验证已运行；已在真实 ScriptCat 安装并验证部分行为，私有仓库和原定兼容矩阵仍待验收，不能将单一环境结果解释为所有组合受支持。

产品范围见 [产品需求](requirements.md)，授权边界见 [仓库授权](authentication.md)。
模块边界、数据流程与工程初值见 [技术设计](architecture.md)，实施顺序见 [开发计划](development-plan.md)。

## 技术基线

| 领域 | 选型 | 原因与边界 |
|---|---|---|
| 语言 | TypeScript，开启严格检查 | 明确仓库上下文、目录索引、加载与错误状态，减少上下文混用 |
| 构建 | Vite + vite-plugin-monkey | 复用油猴开发、元信息生成和用户脚本打包能力，不自建构建体系 |
| 包管理 | pnpm + pnpm-lock.yaml | 使用用户级共享 store，保持项目依赖声明与安装可复现 |
| 界面 | 原生 DOM + TypeScript | 当前界面集中在文件导航，不默认引入 UI 框架或组件库 |
| 样式 | 原生 CSS + CSS 变量 | 实现布局和明暗主题，不引入 Tailwind 或皮肤系统 |
| 样式隔离 | Shadow DOM | 减少与 GitHub 样式相互干扰；不是凭据安全边界 |
| 请求 | GM.xmlHttpRequest + GitHub REST API | 使用脚本管理器的请求能力，支持显式 PAT、响应头读取及取消请求 |
| 设置与凭据 | GM.getValue / GM.setValue 等 GM 存储 API | 使用脚本管理器存储，不放进 GitHub 页面的 localStorage |
| 目录缓存 | 内存索引 + 有容量边界的 GM 持久化缓存 | 先保持存储方案简单，性能和容量需要实测 |
| 状态组织 | 普通 TypeScript 对象与模块 | 分开组织数据获取、树索引、页面适配和界面更新，不引入状态管理框架 |
| 逻辑验证 | Vitest | 覆盖关键行为与不确定边界，不用模拟环境冒充真实脚本管理器 |
| 分发 | 单个自包含 .user.js | 打包代码和样式，不依赖运行时 CDN、远程 @require 或产品后端 |

## 包管理约定

- 统一使用 pnpm 管理项目依赖与运行开发、构建和测试命令，不继续采用此前建议的 npm。
- 沿用开发环境现有的用户级共享 pnpm store；项目不另建下载缓存，也不单独覆盖 store 路径。
- 不为包缓存创建项目级 store-dir 配置，不将开发者机器上的绝对缓存路径写进仓库。
- 实施时由项目的 package.json 声明依赖，并提交生成的 pnpm-lock.yaml；不并存其他包管理器的锁文件。
- 共享 store 不等于全局安装依赖；TypeScript、Vite、vite-plugin-monkey、Vitest 仍作为项目开发依赖管理，不依赖机器上全局安装的工具版本。
- 项目仍会正常生成 node_modules 及 pnpm 的链接／虚拟 store 结构；不为“使用全局缓存”而手工复制包、跳过项目安装或改变依赖解析方式。
- pnpm 依据文件系统能力从共享 store 链接、克隆或复制文件，不能将共享 store 理解为任何环境下都保证零复制。

## 构建与运行

开发依赖和用户运行时依赖分开评估：完善的本地构建工具不等于发布脚本包含整套构建工具。

- 开发阶段可运行 Vite 本地开发服务器；它不是用户使用产品时需要部署的后端。
- 发布产物为一个可由脚本管理器安装的 .user.js，正常运行不需要开发服务器。
- 生产脚本不通过远程 @require 加载库，也不依赖运行时 CDN。
- 不在脚本中硬编码用户 PAT、应用 secret 或开发机器的路径。
- 具体依赖版本需按 Vite 与插件等工具的兼容关系选定并锁定，不无条件追随各依赖的最新版本。

## 界面与数据

选择原生 DOM 是为了控制依赖和节点更新，不是把全部逻辑堆在一个脚本文件中。

- 数据获取、目录索引、页面适配、界面更新按职责组织，不建设通用插件系统或组件框架。
- 目录树与文件名／路径查找复用同一份索引；加载规则见 [目录预加载](directory-preloading.md)。
- 预加载整个目录索引，不等于一次创建整仓库的 DOM；只渲染当前展开、需要展示的部分。
- 页面适配集中处理 GitHub 站内导航和主题变化，避免把页面结构依赖散落在业务模块中。
- Shadow DOM 只隔离样式。Token 配置使用页内弹窗，新输入及回填的已存 Token 与 GitHub 共享 DOM，页面脚本可读取；默认遮罩，输入框内右侧眼睛按钮切换显隐。提交／关闭时清空，不写入页面存储、侧栏状态或日志。

## 请求与存储

- GitHub 读取接口通过一个小型请求模块调用，不引入 Axios、Octokit 或通用网络框架。
- 只申请实际使用的 GM 能力和目标域名权限，不使用 @connect * 扩大网络权限。
- 目录请求直接发往 GitHub，授权与凭据使用遵循 [仓库授权](authentication.md)；不引入项目授权后端。
- 目录索引按仓库和实际版本缓存，不在每次展开目录时重写整份持久化索引。
- GM 存储不是加密保险箱，仍需明确凭据保存、清除、过期和错误提示的具体行为。
- 当前逻辑预算为总计 16 MiB、单快照 4 MiB；超出时完整内存索引继续可用。真实 GM 存储序列化／传输成本尚未测得，JSON 成本单列在下方，不冒充 GM 成本。
- 当前不引入 IndexedDB、Dexie 或压缩库。只有实际数据证明现有方案无法满足需求时，才重新评估存储复杂度，而不是提前引入第二套方案。

## 验证与兼容

- 使用 Vitest 验证树索引、路径处理和缓存完整性等关键逻辑；用例围绕消费者可见行为与不确定边界设计。
- 在真实脚本管理器中验证安装权限、PAT 请求、站内导航和侧栏行为，不能仅在普通网页中模拟 GM API 就宣称兼容。
- 桌面 Chrome、Edge、Firefox 为兼容目标，优先验证 Tampermonkey 与 Violentmonkey；这些是目标，不是已通过验证的支持声明。
- 最低浏览器／脚本管理器版本、具体兼容矩阵、性能指标和大仓库渲染策略需要在实现验证中确定。
